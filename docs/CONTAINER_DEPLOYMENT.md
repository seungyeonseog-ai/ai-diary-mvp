# 단일 서버 Docker Compose 운영·검증

이 문서는 2026-11-04 로컬 Linux 컨테이너에서 확인한 실행 경로다. 빌드·서비스 실행·영속 데이터 재생성/복원과 실제 AI 연결을 확인했다. 외부 서버 선정·공개 배포·HTTPS 프록시는 후속 작업이다.

## 구성과 데이터

- Python 3.12 + 고정 Python 의존성/CPU Torch 이미지. Chroma도 같은 이미지의 1.0.15 CLI 서버로 실행한다. Python 기반 이미지와 Redis7.4는 검증한 digest로 고정했다. Linux amd64에서 확인했으며 다른 아키텍처의 실행 성공을 추정하지 않는다.
- `db-init`는 새 빈 DB의 전체 스키마/날짜 작업 활성화를 준비한다. 기존 DB는 검사만 하며 자동 이행/초기화하지 않는다. 명시적인 `migrate`에만 먼저 온라인 백업을 만든다. 부분 이행 실패 시 기존 자료를 지우거나 빈 DB로 대체하지 않는다.
- `model-init`는 CPU 임베딩 모델을 준비한다. 웹/Worker/Beat는 준비 완료 후 오프라인 캐시를 사용한다.
- `app_data`에는 **app.db와 sparse_fts.db 및 WAL 관련 파일**을 함께 둔다. 사진은 app.db의 인증 대상 BLOB이다. 웹/Worker/Beat가 동일 볼륨을 공유한다.
- Chroma는 `/chroma-data`, Redis는 `/data`의 AOF, Beat는 `/state` 스케줄 파일을 각각 별도 이름 있는 볼륨에 둔다. Beat PID는 `/tmp`에 두고 공유 `/state/beat.lock`의 OS 잠금으로 중복 실행을 거부한다.
- Redis/Chroma의 호스트 포트는 공개하지 않는다. 웹만 기본 `127.0.0.1:18000`으로 바인딩한다. 원본 Windows 서비스 8000/8001/6379와 다른 실행 경로다.
- `docker compose down -v`, `docker volume prune`는 운영 절차에 사용하지 않는다. 프로젝트명 변경은 다른 볼륨을 선택하므로 빈 서비스가 보인다고 데이터를 초기화하지 말고 기존 프로젝트명·볼륨을 먼저 확인한다.

## Linux 서버 시작·중지

서버에 Docker Engine과 Compose, 호스트 Python 3가 필요하다. 유료 Docker Hub 계정은 필수가 아니며 서버에서 이미지를 직접 빌드한다.

1. `cp deploy/production.env.example .env.production`
2. 실제 API 키, 독립적인 난수 SECRET_KEY(32자 이상), 프로젝트명, 필요 포트를 설정한다. 파일 권한을 제한하고 Git/이미지/로그에 넣지 않는다. 기존 로컬 .env와 DB를 자동으로 가져오지 않는다.
3. `sh start.sh` 또는 `python3 -m deploy.compose start`
4. `python3 -m deploy.compose check`
5. 중지는 `sh stop.sh`. 컨테이너/볼륨을 남겨 둔다.

`start`는 config --quiet → build → up --no-build --wait 순서다. 기존 서비스를 먼저 down 하지 않으며, 초기화·의존 서비스·웹/Worker/Beat 상태 검사 실패를 종료 코드로 전달한다. 이미지 교체 시 필요한 컨테이너 재생성으로 짧은 서비스 중단은 있을 수 있으며 무중단 배포를 보장하지 않는다. 누락된 키는 Compose 검사에서, 기본/짧은 비밀값·잘못된 데이터 경로는 초기화 사전 검사에서 차단한다.

기존 DB 이행이 필요하면 먼저 외부 백업과 서비스 중지를 확인한 후 `db-init`의 명시적 migrate 명령을 사용한다. 무조건 전체 테이블을 새로 만드는 우회는 하지 않는다. 이행 전 백업은 같은 데이터 볼륨에 생성되므로 서버 밖 백업을 대체하지 않는다.

## 백업·복원

`sh backup.sh` 또는 `python3 -m deploy.compose backup --archive /private/backups/pilot.tar.gz`

- 실행 중인 해당 프로젝트 서비스를 중지한 뒤 app/FTS, Chroma, Redis, Beat 상태를 동일 시점의 파일 집합으로 압축한다. 파일 해시 manifest와 SQLite 무결성 검사를 포함한다.
- 비밀 환경파일과 재다운로드 가능한 모델 캐시는 포함하지 않는다. 환경 비밀값은 별도 안전한 경로로 보존한다. 백업 파일 자체는 대화/일기/사진을 포함하므로 비공개 취급하며 접근 권한을 제한한다.
- 중간 실패는 종료 코드로 전파한다. 서비스 재시작은 finally 경로에서 시도한다. 중지형 백업이므로 백업 중 서비스가 일시 중단된다.
- 백업은 생성 후 서버 밖 저장소로 보관해야 한다. 현재 작업은 외부 저장소 생성/주기 작업 등록을 하지 않는다. 백업 주기에 따른 최대 손실 구간과 복구 시간을 별도로 정해야 한다.

복원은 **별도 프로젝트의 빈 볼륨**에서 한다.

`python3 -m deploy.compose restore --project matabus-restore-test --archive /private/backups/pilot.tar.gz`

실행 중인 프로젝트나 내용이 있는 대상 볼륨은 거부한다. 전체 archive의 경로/종류/중복/해시와 DB 무결성을 확인하고 복원한다. 새 프로젝트에서 모델을 준비한 후 앱을 시작해 로그인·일기·사진·검색·예약 상태를 확인해야 복원 성공으로 판단한다. 원래 볼륨을 삭제해 복원 공간을 만드는 절차는 없다.

## Windows 로컬 격리 검증

- 기존 Windows WSL 2 기능은 재설치하지 않았다. 등록된 배포판이 없는 상태에서 Ubuntu 24.04를 추가하고, 그 안에 Docker Engine/Compose를 설치했다. Windows를 교체하거나 로컬 DB를 옮긴 것이 아니다.
- Docker 자동시작은 해제했다. WSL 작업 종료에 따른 유휴 종료를 피하려고 검증 중 dockerd를 명시적인 실행 세션에서 유지한다. Windows 부팅 작업/스케줄은 등록하지 않는다.
- PC 메모리는 약8GB, WSL에 보이는 메모리는 약3.7GB다. 기존 서비스를 유지하며 검증하므로 속도·메모리 제약을 실제 측정한다. 이 수치를 서버 권장 사양으로 일반화하지 않는다.
- `.local-check/docker-validation/validation.env`의 합성 키·별도 이미지/프로젝트/18000 포트만 쓴다. 실제 .env/키/DB/인덱스를 마운트하지 않는다.
- `sh deploy/run-validation.sh config --quiet`, `build web`, `up -d --no-build --wait --wait-timeout 900` 순서다. 명령은 Ubuntu 안에서 프로젝트 루트 경로를 사용해 실행한다.
- 검증 target만 `validation.runtime`를 포함한다. 제품 main/인증/DB/Redis/Chroma/Celery 경로는 실제이며 AI 생성 경계만 합성이다. SDK 외부 AI 주소도 차단한다. 이것은 실제 외부 AI 연결/내용 품질 검증과 구별한다.
- 자동 검사는 `python -B -m unittest tests.test_deployment -v`. Windows에서는 PYTHONUTF8/PYTHONIOENCODING을 설정한다.

## 실제 AI를 포함한 통합 검증

사용자 합의로 1번 배포 환경 검증과 2번(기존9번 실제 연결)을 Docker18000에서 통합한다. 합성 target의 실제 인증/저장/스케줄러 경로는 재사용하고 `docker-compose.real-validation.yml`을 명시적으로 추가할 때만 생성 경계를 실제 AI로 전환한다. 제품 runtime 이미지에는 검증 모듈/기간 조정 API가 들어가지 않는다.

- `tests/deployment/prepare_real_env.py`는 기존 로컬 키를 출력하지 않고 Git 제외 `real.env`에 전달한다. 프록시 컨테이너만 실제 키를 받으며 앱은 합성 키와 내부 프록시 주소를 쓴다. host 포트는 공개하지 않는다. 이 환경은 합성 계정 전용으로만 사용한다.
- `sh deploy/run-real-validation.sh up -d --no-build --wait --wait-timeout 900`. 종료 시 같은 wrapper의 `stop`을 사용한다. 실제 키가 포함된 `config` 전체 출력/inspect 환경 출력은 하지 않는다.
- 프록시 상한은 고정 gpt-5.6-luna, 누적30호출(실패/중단 포함), 회당 JSON60000바이트/출력1800토큰, n=1·도구 금지. 호출 예약은 별도 SQLite 볼륨에 저장해 재시작으로 초기화하지 않는다. 경계/영속 상한 검사2개 통과. 공식 입력0.20/출력1.20달러 per1M 기준 보수적인 전체 상한도1달러 미만이며, 사용자 승인 상한은 이번 검증 누적2달러다. 실제 사용량/결과는 완료 후 별도로 기록한다.
- 실제 AI 여정 검사는 `python -m tests.deployment.verify_real_http`. 사용자 원문 대신 합성 자료만 전송하고 기록에는 계정 식별자/집계/시간/해시만 남긴다. 실행 전까지 실제 호출 성공을 추정하지 않는다. 자연 주간 조건은 별도 기간 관찰이다.
- 요금 근거: https://developers.openai.com/api/docs/models/gpt-5.6-luna (2026-11-04 확인).
