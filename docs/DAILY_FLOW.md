# 6번 예약 요약·기억·응원·자정 처리

기준: 2026-11-03. `../outputs/generation-rules-2026-11-02.md`의 최신 후속 사용자 결정이 과거 규칙보다 우선한다.

## 사용자 동작

- 응원 기본 22:00 KST, 첫 로그인 후 메인에서 시간 설정 폼. 설정 메뉴에서도 1시간 단위 변경. 이미 받은 날은 다음 날부터, 미수신 상태에서 지난 시각으로 변경하면 변경 순간 입력으로 즉시 작업을 등록한다(Worker 점검은 최대 약 1분 간격).
- 예약 시각에 사용자 대화가 없으면 그날 응원은 건너뛴다. 나중에 대화해도 자동 보충하지 않는다. 시각을 명시적으로 다시 설정한 경우는 변경한 예약을 적용한다.
- 응원은 날짜당 하나. 폐기해도 재발급하지 않는다. 당일 장애 복구는 가능하지만 다음 날 전날 응원을 새로 생성/발행하지 않는다. 생성 요청 중 자정을 넘긴 응답도 전날 편지로 신규 발행하지 않는다.
- 생성 직후 오늘 받은편지에만 표시한다. 저장하면 동일 결과를 보관함에서도 보여주며 당일 받은편지는 유지한다. 자정에는 오늘 받은편지를 비활성화한다.
- 미저장 편지는 별도 알림 목록/상세에서 이후에도 접근 가능하다. 폐기는 받은편지/처리대기 목록에서 숨기고 보관 등록하지 않는다. 보관함 삭제는 별도 동작이며 당일 받은편지를 동시에 삭제하지 않는다.
- `viewed_at`는 실제 열람 기록일 뿐 저장·폐기 또는 숫자 배지 확인과 같지 않다. **열람만 하고 닫았을 때 자동 소멸/재안내 정책은 사용자 유보**다. 현재 자동 처리나 강제 재안내 없이 명시적 저장/폐기 기능을 제공한다. 최종 유지 기간을 확정한 것으로 해석하지 않는다.
- 접속 중 새 결과는 도착 컴포넌트로 안내한다. 서재 숫자는 서버 결과 ID 기준이며 서재 첫 진입 시 조회했던 ID까지 확인한다. 그 뒤 도착한 새 결과는 다시 숫자로 표시한다. 편지 상세 열람/보관, 차트 렌더 완료와 분리한다.
- 카카오·모바일 구현은 포함하지 않는다. 편지 결과와 표시/알림 상태가 분리돼 후속 알림 채널에서 같은 결과 ID를 열 수 있다.

## 날짜별 작업과 복구

`DailyJob`의 사용자/원본날짜/단계 키는 하나다. 매분 Beat 확인은 여러 논리 요약을 생성하는 것이 아니라 예약/자정 작업의 등록·실패 복구다.

1. 예약 경계 이전 원문 ID를 먼저 고정한다. 일기 폐기 여부와 무관하게 `user` 원문을 사용한다.
2. 요약 AI 응답을 체크포인트로 보관하고 `SummaryRange` 및 검색 호환 요약을 저장한다. 응원 실패가 요약 성공을 취소하지 않는다.
3. 오늘 요약으로 기존 Sparse/Dense·RRF·12후보/버킷최대4 선별을 재사용한다. 본인 과거 날짜 요약만 응원에 넣는다. 후보 중복점유·Sparse 표현 민감도 개선은 별도 과제로 유지한다.
4. 응원 입력은 오늘 원문과 검색한 과거 요약이다. 요약/검색 실패 시 오늘 원문으로 응원을 제공하고 요약·기억을 별도 복구한다. 정상 0건과 오류는 엄격 검색 경로에서 구별한다. 기존 전등 대화 검색의 오류 정책/순위는 바꾸지 않는다.
5. 응원 응답 체크포인트→기존 `EncouragementReport` 한 행→`LetterDelivery` 및 `ResultNotice`를 같은 트랜잭션으로 커밋한다. 발행 오류는 편지를 재생성하지 않는다.
6. 자정 이후 전날 원문을 조회하되 예약 작업이 예약/처리한 ID와 성공 요약 ID는 제외한다. 첫 요약이 실패했다면 그 작업에서 같은 ID를 복구하고, 자정 작업은 나머지 추가분만 처리한다. 실제 결과는 날짜별 0~2구간이다.
7. 인덱싱은 안정적인 날짜구간 세션 ID/문서 ID로 Chroma와 FTS에 upsert한다. 원래 기술 채팅 세션을 조작하지 않고, 원본 날짜와 끝점이 연결된 별도 날짜구간 로그를 만든다.

동시 실행은 DB 트랜잭션과 15분 lease/fencing으로 차단한다. 외부 호출은 60초 제한·SDK 자동 재시도 없음, 실패 작업은 2→4→8…최대60분 간격으로 재시도한다. 응원은 날짜 경계를 넘으면 생성하지 않고 요약 복구만 지속한다. 체크포인트 이후에는 성공 AI 단계를 반복하지 않는다. 프로세스가 외부 API 응답 직후 DB 체크포인트 이전에 강제 종료되는 경우처럼 외부 API와 로컬DB 사이의 불확실한 완료를 완전한 exactly-once 호출로 보장하는 것은 아니다. DB 결과의 날짜 유일성/lease와 응답 체크포인트로 중복 발행을 차단한다.

3분 종료 요약은 main의 루프 연결 및 종료 리스너에서 해제했다. 브로커에 남은 구형 `session_summarize_task`도 no-op으로 처리한다. 기존 세션 자료와 검색 인덱스는 보존한다. 주간 자격/3탭 개편은 다음 7번이다.

## DB 이행과 하루 일기 하나

`python -m tools.migrate_daily --database .local-check/test.db`

- 온라인 백업 후 새 테이블·중복 방지 트리거를 추가한다. 기존 복수 일기를 삭제/병합하는 것보다 신규 저장을 강제하는 방식이 단순해 기존 자료를 남긴다.
- 일기는 사용자/동일 KST 날짜의 유효본 하나다. 새 초안 생성·직접 작성·폐기 상태 복원에서 신규 중복을 막는다. 기존 동일날 복수 자료의 단순 본문 수정은 가능하다. 폐기 후 새 작성은 가능하며 원문은 보존한다.
- 당일 기존 일기가 있으면 `/writing`은 그 일기를 연결해 연다. 다중 탭의 새 작성은 같은 작성 ID를 재사용한다. 서버 트랜잭션과 DB 트리거를 함께 적용한다.
- 기존 응원은 날짜별 최신 한 건만 새 표시 상태와 연결하며 기존 본문/결과는 수정·삭제하지 않는다. 새 응원 행은 DB에서도 사용자/날짜 중복을 막는다.
- 이행 전후 일기/대화/계정 원본 해시와 SQLite `integrity_check`를 확인한다. 복구하려면 서비스를 중단한 상태에서 해당 백업을 사용한다. 동작 중 DB 파일을 덮어쓰지 않는다.

## API/화면

- `/daily/settings` GET/PUT: 본인 시각/적용일. hour 0~23 정수. 00시는 그날 시작 경계이므로 그날 대화가 없으면 생성하지 않는 동일 규칙이 적용된다.
- `/daily/inbox`: 오늘 활성 편지/상태. `/daily/letters?view=pending|archive`: 목록.
- `/daily/letters/{id}` GET, `/{view|save|discard|archive-delete}` POST: 본인 결과만 조작.
- `/daily/notices` GET 및 `/daily/notices/seen` POST: ID별 영속 배지/스냅샷 확인. 편지 원문은 알림 속성에 넣지 않는다.
- `/letters`: 오늘 받은편지/보관함. 공통 `daily.js`가 설정·별도 알림 창/동일 편지 상세 디자인을 제공한다. 캐릭터 계정 역할은 유지하고 별도 편지 알림 버튼을 추가했다.
- WebSocket 기존 채널을 유지하고 커밋된 알림의 발행 실패를 재시도한다. 15초 폴링/화면 복귀 조회로 누락을 복원한다. 동일 ID 재발행은 새 숫자로 더하지 않는다.
- 기존 `/study/status`, `/study/encourage` 응답 형식은 유지하며 새 상태를 반영한다. 구형 화면은 응원 조회 가능하지만 새 보관/설정/미확인 목록은 갱신한 새 UI에서 사용한다. 자산 버전 `20261103-6a`, 열린 구형 화면은 새로고침이 필요하다.
